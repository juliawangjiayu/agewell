## 一、目标与主张

用一个网页版三人群聊，展示一个**照护判断引擎**：看得最久的女佣说一句话，系统决定这件事重不重要、该让谁知道、该怎么说；反方向，雇主布置一句含糊指令，系统拆成女佣能确认的逐项任务。

**要证明的核心命题**：产品的价值不在"语义理解 + 任务分解 + 跨语言生成"（这是通用大模型的商品化能力），而在其上的**判断层**——分级、相关方判定、差异化改写、确认闭环。这一层才是护城河。

---

## 二、范围

### 做（且只做）这三个场景 + 语音
1. **On-board**：雇主与女佣各自录入基础信息，Bot 建立家庭上下文库。
2. **故事 A · 女佣→雇主**：观察 → 分级/升级判断 → 相关方判定 → 差异化输出。
3. **故事 B · 雇主→女佣**：含糊指令 → 任务分解 → 跨语言生成 → 逐项确认闭环。
4. **语音**：女佣/雇主端语音输入、老人端语音输出，均由具备语音能力的强模型直接处理（见第九节）。

### 明确不做
趋势图、用药管理工具、预约挂号、多家庭管理、账号体系、老人端 App（老人只通过语音被动知情，不上屏操作）、跨人群校准。

> 纪律：demo 里出现的任何第二条判断链路都在稀释核心主张。新功能一律不加。

---

## 三、角色与界面

| 角色 | 语言 | 界面 | 说明 |
|---|---|---|---|
| 雇主 | 中文 | 三人群聊（可文字/语音输入） | 白天上班，数字能力强 |
| 女佣 Rosa | Tagalog（含 "eat small small" 式英菲混说） | 三人群聊（可文字/语音输入） | 菲律宾籍，沿用文档人设 |
| Bot | 双向 | 群聊内以第三方身份发言 | 判断引擎的对外形态 |
| 老人 Ah Ma | 中文（听） | **不上屏**，仅语音输出 | 82 岁，HDB，与女儿同住 |

**产品形态**：单页 WhatsApp 式三人群聊 Web 应用。老人不作为聊天参与者出现，只在触发升级/每周摘要时通过语音被告知。

## 四、架构

```
              ┌─────────────────────────────────────┐
   雇主(中文)─┤                                     │
              │   一个 Agent · 按发信人角色路由      │
   女佣(Tag)─┤                                     │
              │   ├── 女佣流：观察 → 分级 → 通知     │
              │   └── 雇主流：指令 → 拆解 → 确认     │
              └───────────────┬─────────────────────┘
                              │  共享
                    ┌─────────▼──────────┐
                    │   家庭上下文库      │  ← On-board 建立
                    │  (基线/用药/近期观察)│
                    └─────────┬──────────┘
                              │
                    ┌─────────▼──────────┐
                    │   判断层（强模型）  │  = 护城河 = "skill"
                    └────────────────────┘
```

- **一个 agent，两条流**：不是两套引擎。发信人是雇主走拆解流，是女佣走分级流，共用同一上下文库。这对应访谈结论"同一个判断层，跑两个方向"。
- **"女佣 skill / 雇主 skill" 是对外推广叙事**：便于宣传"谁都能接一个 AI API + 我们的 skill + WhatsApp 接口"。底层实现是单 agent 角色路由，不要让营销切分把架构搞乱。
- **判断层的护城河定位**：skill 本质是被产品化、可分发的结构化指令（prompt + 领域知识）。它是判断层的**分发形态，不是护城河本身**。护城河是 ① 具体的（未来经临床验证的）分级启发式；② 随时间积累的这个家庭的上下文库。**对评委的说法：skill 是我们判断层的分发机制，价值在里面装的判断，不在"能写 prompt"。**

## 五、家庭上下文库（数据模型）

On-board 阶段建立，两条流共享读取。

```
FamilyContext {
  elder:      { name, age, conditions[], baseline_notes }
  medications: [ { name, timing(饭前/饭后/睡前...), clock_time, notes } ]
  followups:  { clinic, interval, next_date, last_med_change_date }
  household:  { members[], who_manages_kitchen, primary_caregiver }
  helper:     { name, home_country, mother_tongue, care_abilities[] }
  recent_observations: [ { date, raw_text, restored_text, grade } ]         // 运行时累积
}
```

- `recent_observations` 是分级判断的关键上下文——同一句"没胃口"是第一次还是第三次，全靠它。
- `last_med_change_date` 是故事 A 升级判断的触发锚点。

### 具体占位内容（可直接进 demo；`[]` 内为需人审替换项）

> 说明：以下是已编好的具体人设与数字，直接用于 demo 展示文字；`[方括号]` 标出的是需要真实数据核对/替换的项，方便人审时定位。

```

          conditions: ["[高血压]", "[2 型糖尿病]"],
          baseline_notes: "平时三餐正常，能自己走动，晚饭后爱看电视" }
```

## 六、场景一：On-board

### 雇主录入
- 老人基础信息：姓名、年龄、慢病。
- **用药表**：药名 · 饭前/饭后/时间（具体内容见第五节"具体占位内容"，`[]` 项需人审替换）。
- 复诊节奏、最近一次调药日期。
- 家庭结构：几口人、谁管厨房、谁是主要照护者。

### 女佣录入 —— 用语纪律（重要）
录入她的**母语/来源国**和**基础照护能力**，但：

> **界面用语必须口语、暖场、不能出现"技能""考核""填报"这类词**——她可能根本听不懂"技能"。

用她的母语这样问：
- "你以前照顾过长辈吗？"
- "会不会帮忙翻身、量血压？"
- "平时会做哪些菜？"
- 整体框成"**帮你把这份工作做顺**"，不是一张能力评估表。

这直接对应访谈：会被接受的是"帮她把工作干好"，会被抵触的是"要求她定期填报/记录她做了多少"。**On-board 的第一印象就要立住"减负不监控"的定位。**

### 老人
不上屏，由雇主代录基础信息。

### 产出
Bot 汇总成 `FamilyContext`，并在群里用双语发一条温和的开场，确认信息已就位。

## 七、场景二：女佣→雇主 · 分级/升级判断（故事 A）

### 链路
```
Rosa 输入(Tagalog/混说)
  → ① 跨语言语义还原（"eat small small" → 进食量减少约 50%）
  → ② 上下文检索（用药史 / 近期观察 / 复诊节奏）
  → ③ 分级（记录 / 常规通报 / 即时升级）
  → ④ 相关方判定（子女 / 医生 / 都不通知）
  → ⑤ 差异化输出
```

### 三层分级（绝大多数落第一层是产品主张，不是能力不足）
| 层级 | 处理 | 预期占比 |
|---|---|---|
| 记录 | 不通知任何人，进上下文库 | ~85% |
| 常规通报 | 每日汇总，不打断 | ~12% |
| 即时升级 | 打断，定向送达 | ~3% |

### 高光屏："同一句话，不同结果"
输入固定为「Ah Ma 今天没什么胃口，午饭只吃了半碗」，并排展示上下文如何改变结论：

| 上下文条件 | 分级 | 通知对象 | 理由 |
|---|---|---|---|
| 孤立事件 | 记录 | 无 | 单次波动不构成信号 |
| 连续 3 天 | 常规通报 | 子女 | 持续性改变 |
| 三天前刚调药 | 即时升级 | 医生 | 时间关联提示药物反应 |
| 同时明显嗜睡 | 即时升级 | 医生+子女 | 症状组合优先级更高 |

**UI 必须显式打出「分级标签」+ 一行「为什么」**，让评委一眼看到这是上下文推理，不是关键词匹配、不是翻译 API。

### 具体演示内容（Day 5 高光 · `[]` 需人审）
**Rosa 语音输入（Tagalog/混说）**：
> "Ma'am, si Ah Ma po, ayaw kumain masyado today, tanghali kalahati lang... tapos sabi niya medyo nahihilo siya."
> （系统还原：Ah Ma 今天没什么胃口，午饭只吃了半碗，还说有点头晕。）

**系统判断（显式打在屏上）**：
> 🔴 **即时升级** → 医生 + 子女
> 为什么：[Day 3] 刚上调降压药 [Amlodipine]，头晕是该药已知反应；食欲下降本周第 [3] 次。时间关联 + 症状组合，优先级高于单一症状。

### 差异化输出（同一事实，三种写法，`[]` 需人审）
- **给子女（丽珍）**：
  > 妈妈今天午饭吃得少，这是本周第 [3] 次了，还说有点头晕。[周三] 医生刚把降压药 [Amlodipine] 加了量，可能有关系。今晚回家可以问问她头晕是站起来的时候还是一直晕，另外 [周五] 复诊记得提一下这件事。
- **给医生**（结构化、去情绪、带临床标注）：
  > 患者女性 [82] 岁，[高血压 / 2 型糖尿病]。[Day 3] 上调 [Amlodipine 5→10mg]。此后本周 [3] 次进食量减少约 50%，[Day 5] 主诉头晕。无发热、无呕吐。照护者观察，未经临床评估。
- **给 Rosa**（一条明确下一步 + 减负确认）：
  > 好的 Rosa，我记下了，你做得对。接下来这两天麻烦留意她还晕不晕、吃了多少，如果她想吐或站不稳，马上告诉我。这件事我会替你整理好，[周五] 看医生前交给女儿。

## 八、场景三：雇主→女佣 · 指令拆解 + 确认闭环（故事 B）

### 链路
```
雇主输入（含糊、混着几件事的中文）
  例：「今晚四个人吃饭，妈妈的药记得饭前，6 点要炒菜就早点准备」
  → ① 语义理解
  → ② 任务分解（拆成独立可执行项）
  → ③ 跨语言生成（Tagalog）+ 挂上时间点
  → Rosa 端呈现为逐项任务
  → ④ Rosa 确认的不是「嗯」，是【逐项确认】
```

### 高光
把没有信息量的「嗯」变成**有信息量的逐项确认**。这是访谈刚验证过、最诚实、群聊里最直观的一屏。

对应访谈：断点是"她只会嗯嗯嗯——信息传了但没人知道有没有接住"。

**雇主输入（中文）**：
> 今晚四个人吃饭，妈妈的药记得饭前吃，[6] 点要炒菜就早点准备。

**系统拆解 → 发给 Rosa（Tagalog，此处中文示意，`[]` 需人审）**，把"嗯"变成可核对的项：
- ☐ 今晚 [4] 人晚饭
- ☐ Ah Ma 的 [降压药] —— **饭前**吃（约 [17:30] 晚饭前）
- ☐ [17:00] 开始备菜（[18:00] 炒）← 体现"提前量"，对应访谈"5 点告诉她不要 5 点半"

Rosa 逐项打勾确认，雇主端看到的不再是"嗯"，而是三项都被接住了。

### 纯 AI 才做得到
理解含糊、口语、混着几件事的中文指令，拆成可执行项，翻成她的语言并挂时间点——语义理解 + 任务分解 + 跨语言生成，规则/模板做不了。**但记住：可替代性的证明在"判断/拆解得对不对"，不在"会翻译"。**

## 九、语音（由具备语音能力的强模型直接处理，不用 Web Speech API）

**决策**：语音输入与输出都交给**能听会说的多模态强模型**（原生接受语音输入、生成语音输出），不走浏览器 Web Speech API。

**为什么不用 Web Speech API**：
- 浏览器 STT 对 Tagalog / 英菲混说的口语识别差，会把 "eat small small" 转成一串错字，**跨语言语义还原那一屏直接崩掉**。
- 强模型是"**听音频 → 直接理解并还原**"一步到位，语音里的犹豫、语气、混语都进了判断层，还原质量远高于"先转错字再理解"。这反而**强化**了核心主张：不可替代的是语音理解，不是转写。
- 老人端 TTS 用强模型合成，中文更自然、更适合 82 岁听感。

### 语音输入（女佣/雇主端）
- 群聊输入框支持按住说话，音频直接送进强模型做理解/还原/判断。
- 价值：强化"她说一句就行"，降低女佣打字门槛。

### 语音输出（老人端）
- 触发即时升级时：语音读出「这件事我需要告诉你女儿」——**告知，不请求许可**。
- 每周摘要：语音读出「这周你女儿知道了两件事：你胃口不太好，还有说有点头晕」。
- 老人端设计原则（对应访谈修正）：老人妥协的动机是**保护子女、不想麻烦人**，所以老人端是**默认呈现的知情**，不是"需要主动行使的否决权"。批注/否决机制保留但不作主通道。

## 十、贯穿全程的定位纪律

| 维度 | 是 | 不是 |
|---|---|---|
| 对女佣 | 替她承担判断、帮她少犯错、出错前提醒 | 考核她汇报够不够、记录她做了多少 |
| 对老人 | 默认让她知道被看见了什么 | 需要她操作才生效的权利 |
| 对雇主 | 把成熟家庭的照护经验变成默认能力 | 一个监控女佣的工具 |

UI 文案和 Bot 话术都要体现，这是社会影响评分项。

### 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | React（腾讯 **CodeBuddy** 生成/集成） | 三人群聊 UI + 老人端语音视图；`MediaRecorder` 采集音频 |
| 编排 | Python **FastAPI** 单进程 | Router 角色分流 + Orchestrator 组 prompt 调模型 |
| 判断层 | 两个 **skill**（系统指令 + 领域知识） | 护城河；由 Orchestrator 注入模型 |
| 模型 | **具备语音能力的强模型 API** | 语音输入理解 + 强推理 + 语音输出一体（见第九节） |
| 数据 | **SQLite** 单文件 + 本地文件存音频 | 见下 |

### 家庭上下文库：为什么是 SQLite

- **单家庭、结构化、数据量极小**（用药 3–5 条、观察 <10 条）。SQLite 单文件、零运维、原生结构化查询，正好。**不需要也不该上向量数据库**——那是过度工程，还会让"上下文检索"显得像 RAG 花活而非真判断。
- **表结构**：`elder / medications / followups / household / helper / observations / messages`，对应第五节数据模型。
- **"上下文检索"在 demo 规模的真实做法**：把整个 `FamilyContext` + 按 `family_id` 时间倒序查出的 `observations` **全量注入 prompt**。无需相似度检索——这是诚实且够用的工程判断。
- **如果继续做**（PPT"下一步"可讲）：多家庭规模后，`observations` 增长再引入向量检索做"近期相关观察"召回；demo 阶段不做。

> 待定：具体用哪个强模型（需同时满足"语音输入 + 语音输出 + 强推理"）留待实现阶段确认。若腾讯工具链模型语音能力不足，判断层/语音用外部强模型，腾讯 CodeBuddy/WorkBuddy 仍做前端生成与集成外壳。
