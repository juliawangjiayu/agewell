## 一、目标与主张

用一个网页版三人群聊，展示一个**照护判断引擎**：看得最久的女佣说一句话，系统决定这件事重不重要、该让谁知道、该怎么说；反方向，雇主布置一句含糊指令，系统拆成女佣能确认的逐项任务。

**要证明的核心命题**：产品的价值不在"语义理解 + 任务分解 + 跨语言生成"（这是通用大模型的商品化能力），而在其上的**判断层**——分级、相关方判定、差异化改写、确认闭环。这一层才是护城河。

---

## 二、范围

### 做的功能
1. **On-board**：雇主与女佣各自录入基础信息，Bot 建库；onboard 后**生成三张常驻 profile 卡片**（雇主 / 老人 / 女佣）。
2. **故事 A · 女佣→雇主**：观察 → 分级/升级判断 → 相关方判定 → 差异化输出。
3. **故事 B · 雇主→女佣**：含糊指令 → 任务分解 → 跨语言生成 → 逐项确认闭环。
4. **对比模式**：一键切换"载入 skill vs 通用好助手裸跑"，同一条输入现场对比（见第八·五节）——AI 不可替代性的现场证明。
5. **语音输入**：女佣/雇主端可语音输入，经 **MERaLiON**（新加坡本土语音模型）转文字后进判断层（见第九节）。
6. **重置按钮**：一键把示例家庭恢复到种子状态，保证黄金路径可从干净起点复现。

### 交付物形态
- **预录视频**：承载高光与老人端语音（可真人配音/任意 TTS），把模型抖动挡在镜头外。
- **公网 demo link**：Vercel（前端）+ Railway（后端 + Postgres）。评委可**自由体验三视角**（onboard / 雇主发言 / 女佣发言）。

### 优先级（3 天，落后就砍）
| 级 | 项 |
|---|---|
| **P0** | 判断层（女佣 skill 分级+相关方+三方输出）、故事 A、故事 B、**对比模式**、上帝视角三人群聊 UI + 身份切换、三张 profile 卡片、onboard、seed 家庭、**重置按钮**、部署上线 |
| **P1** | 语音输入（MERaLiON）、profile 卡片的"模型小结"、三视角切换打磨 |
| **P2→仅视频** | 老人端语音输出、每周摘要、医生端一页摘要 |

### 明确不做
趋势图、用药管理工具、预约挂号、账号/登录体系、老人端 App（老人只被动知情，不上屏操作）、跨人群校准、实时语音输出进 demo link。

> 纪律：demo 里出现的任何第二条判断链路都在稀释核心主张。新功能一律不加。

## 三、角色与界面

| 角色 | 语言 | 说明 |
|---|---|---|
| 雇主（丽珍） | 中文 | Ah Ma 女儿，**与 Ah Ma 不同住**；周五晚~周日团聚，工作日不在场；数字能力强 |
| 女佣 Rosa | **语音说 English/Singlish**（"eat small small"式）；文字可 Taglish 混说 | 菲律宾籍，来两年，工作语言是英语 |
| Bot | 双向 | 判断引擎的对外形态 |
| 老人 Ah Ma | 中文（听） | **不上屏**，语音输出只进视频 |

**产品形态：单一"上帝视角"网页**（不是分屏模拟各自手机）。
- 一屏同时呈现：中间三人群聊全貌 + 侧边**常驻三张 profile 卡片** + 顶部**身份切换器**（以雇主/女佣身份发言）+ 对比模式开关 + 重置按钮。
- 理由：demo 的说服力全在"转化"（含糊→结构化、观察→判断）。上帝视角让评委**在同一屏亲眼看到输入端和输出端同时变化**，冲击力最大，且 build 一套比分屏省一半工。
- 老人不作为聊天参与者出现。

> Rosa 语音改 English/Singlish 的原因：MERaLiON 现不支持 Tagalog（仅 English/Singlish、Malay、Bahasa、Tamil、中文等）；而菲律宾女佣在 SG 的工作语言本就是英语，说 Singlish 比纯 Tagalog 更真实，护城河（跨语域还原→临床中文）一点没减。

## 四、架构

```
   雇主(中文文字/语音) ─┐        ┌─── 上帝视角前端（Vercel / React）
   女佣(Singlish文字/语音)┼───────┤    三人群聊 + 三张profile卡片 + 身份切换 + 对比开关 + 重置
                        │        └──────────────┬──────────────────────
                        │                       │ HTTP（文本 / 音频 blob）
              ┌─────────▼───────────────────────▼──────────┐
              │  后端（Railway / FastAPI）                  │
              │  Router 按发信人角色分流：                  │
              │   ├── 女佣流：观察 → 分级 → 相关方 → 输出   │
              │   └── 雇主流：指令 → 拆解 → 确认            │
              │  Orchestrator（含 skill_on 开关, temp=0）   │
              └───┬───────────────┬──────────────┬─────────┘
       读/写      │        音频→文字│      文本推理 │
        ┌─────────▼──────┐  ┌──────▼──────┐  ┌────▼─────────────┐
        │ Railway Postgres│  │ MERaLiON STT│  │ 判断层强模型      │
        │ 7 张表(见五节)  │  │(女佣/雇主语音)│  │ DeepSeek-V4      │
        └────────────────┘  └─────────────┘  │ = 护城河 = skill  │
                                              └──────────────────┘
```

- **一个 agent，两条流**：不是两套引擎。发信人是雇主走拆解流，是女佣走分级流，共用同一上下文库。对应访谈结论"同一个判断层，跑两个方向"。
- **语音是独立一跳**：MERaLiON 只做"音频→文字"，文字再进判断层。判断层（DeepSeek-V4）只吃文字。两者解耦、各自可测。
- **判断层的护城河定位**：skill 本质是被产品化、可分发的结构化指令（prompt + 领域知识）。它是判断层的**分发形态，不是护城河本身**。护城河是 ① 具体的（未来经临床验证的）分级启发式；② 随时间积累的这个家庭的上下文库。**对评委：skill 是我们判断层的分发机制，价值在里面装的判断，不在"能写 prompt"。**

## 五、数据模型（Railway Postgres）

之前的 SQLite 方案已废弃——demo link 是公网多人可 onboard 的持久服务，而 **Railway 容器文件系统是临时的，SQLite 单文件会在重部署时被清空**。改用 Railway 托管 Postgres，半结构化字段用 `JSONB`（既完善又不过度规范化）。

```
families(id, label, created_at)

employer_profile(family_id, name, language, relation, work_schedule, notes)
elder_profile(family_id, name, age, conditions[jsonb], baseline_notes,
              medications[jsonb], followups[jsonb])
caregiver_profile(family_id, name, home_country, mother_tongue,
                  care_abilities[jsonb])

observations(id, family_id, date, raw_text, restored_text, grade,
             notify[jsonb], reason, created_at)     ← 女佣流判断结果，也是分级上下文
messages(id, family_id, sender_role, content_original, content_rendered,
         meta[jsonb], created_at)                   ← 群聊持久化
tasks(id, family_id, from_message_id, item, time, detail, confirmed)  ← 雇主流逐项确认
```

- **`employer_profile` 是新增的**：三张卡片要求雇主也有 profile（旧 schema 只有 elder + helper）。
- **`observations.notify / reason`** 落库，供 UI 显式展示"通知谁 + 为什么"。
- **职责分工（重要）**：`observations` 只存**精简事实**（date/raw/restored/grade/notify/reason）——它的唯一用途是"未来判断的上下文"，**不存三段 `outputs` 差异化文本**（否则上下文膨胀、干扰下一次判断）。三段 outputs 连同完整判断结果写进 **`messages.meta`**，让群聊+卡片刷新后仍在。**observations = 判断用的精简事实；messages = 展示用的完整记录。**
- **`messages / tasks`** 是硬需求：真·可交互群聊要持久化、确认要落库。
- **`notify` 取值 `family` / `doctor`**（`family` = 家人，不限于子女，可能是配偶/儿媳/亲戚）；`outputs` 三段为 `family / doctor / helper`。
- **"上下文检索"在 demo 规模的真实做法**：把整个家庭上下文 + 按 `family_id` 时间倒序查出的 `observations` **全量注入 prompt**。无需向量库——那是过度工程，还会让"检索"像 RAG 花活而非真判断。多家庭规模后再引入向量召回（PPT"下一步"）。

### 具体种子内容（详见 `docs/demo-seed-story.md`；`[]` 为需人审替换项）
- **雇主**：丽珍，中文，Ah Ma 女儿，**与 Ah Ma 不同住**；一般周五晚接 Ah Ma 吃饭、周六日一起午晚饭，工作日不在场。
- **老人**：[陈亚妹/Ah Ma]，[82]，[高血压]+[2型糖尿病]；**独住 HDB，与 Rosa（住家女佣）同住**，工作日身边只有 Rosa；用药 [Amlodipine 早饭后08:00 / Metformin 早晚饭后 / Losartan 早饭后]；复诊 [每3个月]，next [本周五]，**last_med_change=Day3（周三，[Amlodipine 5→10mg]）**。
- **女佣**：Rosa，菲律宾，与 Ah Ma 同住，语音 English/Singlish；会量血压、照顾过长辈、会做简单家常菜。
- **预置历史**：Day1（周一）/ Day4（周四）两条食欲下降观察（都 `record`）+ Day3（周三）调药 → 让 Day5 头晕的升级"有上下文可依"；这几天丽珍都不在场。
- **叙事要点**：丽珍每周都见 Ah Ma，却不知道工作日发生了什么——**定期在场 ≠ 信息通畅**，工作日只有 Rosa 一双眼睛。这让"看得最久的人说不上话"字面成立，也让升级在丽珍不在场的工作日尤其有价值。

> 医学一致性（供答辩解释链路，非医疗建议）：Day3 上调降压药 [Amlodipine] 后头晕是该类药已知反应，同期食欲下降可与 [Metformin] 肠胃反应叠加——时间关联正是"即时升级"的推理依据，不是关键词触发。

## 六、场景一：On-board（并生成三张 profile 卡片）

### 雇主录入
- 老人基础信息（姓名/年龄/慢病）、用药表（药名·饭前饭后·时间）、复诊节奏、最近一次调药日期、家庭结构（几口人/谁管厨房/谁是主要照护者）、以及雇主自己的 profile（称呼/与老人关系/作息）。

### 女佣录入 —— 用语纪律（重要）
录入她的**母语/来源国**和**基础照护能力**，但**界面用语必须口语、暖场、不能出现"技能/考核/填报"这类词**——她可能根本听不懂"技能"。用她能懂的话问：
- "你以前照顾过长辈吗？" / "会不会帮忙翻身、量血压？" / "平时会做哪些菜？"
- 整体框成"**帮你把这份工作做顺**"，不是能力评估表。

对应访谈：会被接受的是"帮她把工作干好"，会被抵触的是"要求她定期填报"。**On-board 第一印象就要立住"减负不监控"。**

### profile 卡片生成
- **结构化字段是源真相（P0，不经模型）**：卡片直接显示 onboard 填的字段，也是判断层的上下文来源——保证判断稳定，不受生成抖动影响。
- **模型小结（P1，可砍）**：再让模型给每张卡片生成一句人话小结（如女佣卡"Rosa，菲律宾，来两年；会量血压、照顾过长辈、擅长家常菜"），纯装饰，砍了不影响判断。

### 老人
不上屏，由雇主代录。

## 七、场景二：女佣→雇主 · 分级/升级判断（故事 A）

### 链路
```
Rosa 输入（English/Singlish 语音→MERaLiON转文字，或文字）
  → ① 跨语域语义还原（"eat small small" → 进食量减少约 50%）
  → ② 上下文检索（用药史 / 近期观察 / 复诊节奏）
  → ③ 分级（记录 / 常规通报 / 即时升级）
  → ④ 相关方判定（家人 / 医生 / 都不通知）
  → ⑤ 差异化输出
```

### 三层分级（绝大多数落第一层是产品主张，不是能力不足）
| 层级 | 处理 | 预期占比 |
|---|---|---|
| 记录 record | 不通知任何人，进上下文库 | ~85% |
| 常规通报 routine | 通知家人，不打断 | ~12% |
| 即时升级 escalate | 打断，定向送达 | ~3% |

### 高光屏："同一句话，不同结果"
输入固定为「Ah Ma 今天没什么胃口，午饭只吃了半碗」，并排展示上下文如何改变结论：

| 上下文条件 | 分级 | 通知对象 | 理由 |
|---|---|---|---|
| 孤立事件 | 记录 | 无 | 单次波动不构成信号 |
| 连续 3 天 | 常规通报 | 家人 | 持续性改变 |
| 三天前刚调药 | 即时升级 | 医生 | 时间关联提示药物反应 |
| 同时明显嗜睡 | 即时升级 | 医生+家人 | 症状组合优先级更高 |

**UI 必须显式打出「分级标签」+ 一行「为什么」**，让评委一眼看到这是上下文推理，不是关键词匹配、不是翻译 API。

> **三级示例剧本**（demo 会分别展示 record / routine / escalate 三种处理）：见 `docs/skills-draft/helper_skill.md` 的"三级示例"与 `docs/demo-seed-story.md`。record 静默记录（占 ~85%，体现防误报）、routine 通知家人不打断、escalate 打断并定向送医生+家人。

### 具体演示内容（Day 5 高光 · `[]` 需人审）
**Rosa 语音输入（English/Singlish）**：
> "Ma'am, Ah Ma today no mood to eat, lunch eat small small only half bowl… and she say she feel a bit dizzy."
> （系统还原：Ah Ma 今天没什么胃口，午饭只吃了半碗，还说有点头晕。）

**系统判断（显式打在屏上）**：
> 🔴 **即时升级** → 医生 + 家人
> 为什么：[Day 3] 刚上调降压药 [Amlodipine]，头晕是该药已知反应；食欲下降本周第 [3] 次。时间关联 + 症状组合，优先级高于单一症状。

### 差异化输出（同一事实，三种写法，`[]` 需人审）
- **给家人（这里是女儿丽珍，工作日不在场）**：妈妈今天午饭吃得少，这是本周第 [3] 次了，还说有点头晕。[周三] 医生刚把降压药 [Amlodipine] 加了量，可能有关系。今晚可以打个电话或视频问问她，头晕是站起来的时候还是一直晕；[周五] 接她/复诊时记得跟医生提一下。
- **给医生**（结构化、去情绪、带临床标注）：患者女性 [82] 岁，[高血压/2型糖尿病]。[Day3] 上调 [Amlodipine 5→10mg]。此后本周 [3] 次进食量减少约 50%，[Day5] 主诉头晕。无发热、无呕吐。照护者观察，未经临床评估。
- **给 Rosa**（一条明确下一步 + 减负确认）：好的 Rosa，我记下了，你做得对。这两天麻烦留意她还晕不晕、吃了多少，如果想吐或站不稳马上告诉我。这件事我会替你整理好，[周五] 看医生前交给女儿。

## 八、场景三：雇主→女佣 · 指令拆解 + 确认闭环（故事 B）

### 链路
```
雇主输入（含糊、混着几件事的中文）
  → ① 语义理解 → ② 任务分解（拆成独立可执行项）
  → ③ 跨语言生成（Tagalog/英语）+ 挂时间点 → Rosa 端逐项任务
  → ④ Rosa 确认的不是「嗯」，是【逐项确认】
```

### 高光
把没有信息量的「嗯」变成**有信息量的逐项确认**。对应访谈断点"她只会嗯嗯嗯——信息传了但没人知道有没有接住"。

**雇主输入（中文）**：
> 今晚我们四个人过来吃饭，妈妈的药记得饭前吃，[6] 点要炒菜就早点准备。

**系统拆解 → 发给 Rosa**，把"嗯"变成**动作导向、带时间节点**的可核对项：
- ☐ [16:00] 去买菜（今晚 **5 人份**：4 位客人 + Ah Ma）← **系统推断出的前置动作**（雇主没明说）
- ☐ 开始备菜（时间灵活，`time:null`，[18:00] 要能下锅）
- ☐ [17:30] 让 Ah Ma 吃 [降压药]（**饭前**）
- ☐ [18:30] 前开饭（[18:00] 炒，体现"提前量"，对应访谈"5 点告诉她不要 5 点半"）

Rosa 逐项打勾确认，雇主端看到的不再是"嗯"，而是四项都被接住。

> **拆解要点**：① 动作导向（去买菜/备菜/吃药/开饭），不是笼统复述；② 带时间节点，灵活的项（备菜）可不挂死时间；③ **补出必需的前置动作**——"要吃饭"隐含"要先买菜"；④ **推断真实人数**——"我们四个人过来"= 4 客 + 住这儿的 Ah Ma = **5 人**，裸模型会照字面备 4 人份把 Ah Ma 漏掉。③④ 都是"任务分解 ≠ 翻译"的现场证据。

### 纯 AI 才做得到
理解含糊、口语、混着几件事的指令，拆成可执行项、翻成她的语言并挂时间点——语义理解 + 任务分解 + 跨语言生成，规则/模板做不了。**但可替代性的证明在"判断/拆解得对不对"，不在"会翻译"。**

## 八·五、对比模式（一键对比：载入 skill vs 通用好助手裸跑）★

**这是回应"AI 不可替代性 40 分"和"这不就是通用大模型吗"的最强武器——不用嘴解释，现场一键切给评委看。**

### 交互
群聊界面顶部一个开关：**「载入 skill ⇄ 关闭 skill」**。同一条输入，一键切换后对比两种输出。

| | **关闭 skill（通用好助手裸跑）** | **载入 skill（我们的应用）** |
|---|---|---|
| 故事 A | 一段**热心但不分级、不路由、不区分医生/家人、不克制**的泛泛回应 | 🔴 即时升级 + 相关方 + 一行"为什么" + 家人/医生/女佣三方差异化输出 |
| 故事 B | 一段泛泛复述/翻译，"嗯"的问题原样保留——**没有拆解、时间点、逐项确认** | 结构化逐项任务 + 时间点 + 提前量 + 逐项确认闭环 |

### baseline 用"通用好助手"，不用"翻译助手"——诚实即说服力
`skill_on=False` 的 system prompt 是一句**普通人不用我们 skill、直接问 DeepSeek 会给的中性指令**：
> "你是家庭群聊里的助手，帮忙把这条消息传达给家里人。"

**不是**"你只是个翻译"。因为"翻译助手"是稻草人，评委一句"我给通用模型好 prompt 它也能分级"就能捅穿。用"通用好助手"，差别变成**"泛泛热心 vs 结构化判断（分级+相关方+三方差异化+防误报克制）"——真实、可辩护**。

### 答辩纪律（把那一刀变成强点）
> "对，你可以努力 prompt 通用模型让它也这么判断——**而那个 prompt 就是我们的 skill**。我们卖的不是模型，是这套被验证过、可分发的判断。你这句质疑正好说明了我们在卖什么。"

**关键不变量：同一个模型、同一条输入、唯一变量是 skill。** 一定要强调，否则被当成拿弱模型作对比。

## 九、语音（女佣/雇主输入经 MERaLiON；老人端输出只进视频）

**决策**：语音**输入**由 **MERaLiON**（新加坡 AI Singapore 的多语种语音模型）做"音频→文字"，再进判断层；老人端语音**输出**只进预录视频，不进 demo link。

### 为什么是 MERaLiON（而不是浏览器 Web Speech，也不是让强模型直接吃音频）
- 浏览器 STT 对 Singlish/口语识别差，会把 "eat small small" 转成错字，跨语域还原那屏直接崩。
- MERaLiON 是**专用强 STT**，吃 English/Singlish、Malay、Bahasa、Tamil、中文等 SG 语言；在 Age Well SG 赛场用一个新加坡造的语音模型是**叙事加分**。
- DeepSeek-V4 是文字模型、不原生吃音频；MERaLiON 转文字后接现成文字链路，架构更干净、各自可测。
- ⚠️ MERaLiON 现不支持 Tagalog——故 Rosa 语音说 English/Singlish（见第三节）。

调用形态（api.meralion.ai，STT）：
```
POST /v1/audio/transcriptions
{ "audio_url": "data:audio/wav;base64,<BASE64_AUDIO>" }
```

### 语音输入（女佣/雇主端）
- 前端 `MediaRecorder` 录音 → 后端 → MERaLiON 转文字 → orchestrator 文字路径（不变）。
- 前端**同时支持语音和文字**输入，服务端都收敛成文字。
- 价值：强化"她说一句就行"，降低女佣打字门槛。

### 语音输出（老人端）—— 只进视频（P2）
- 触发即时升级：语音读出「这件事我需要告诉你女儿」——告知，不请求许可。
- 每周摘要：语音读出「这周你女儿知道了两件事：你胃口不太好，还有说有点头晕」。
- 视频里用真人配音或任意中文 TTS 实现（MERaLiON 只做 STT，不做 TTS）。
- 老人端设计原则（对应访谈修正）：老人妥协的动机是**保护子女、不想麻烦人**，所以是**默认呈现的知情**，不是"需要主动行使的否决权"。

## 十一、技术架构与技术栈

### 技术栈
| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | **React（CodeBuddy 生成/集成），部署 Vercel** | 上帝视角三人群聊 + 三张 profile 卡片 + 身份切换 + 对比开关 + 重置按钮；`MediaRecorder` 采集音频；同时支持语音/文字输入 |
| 后端 | **Python FastAPI，部署 Railway** | Router 角色分流 + Orchestrator 组 prompt 调模型（**temp=0**） |
| 判断层 | 两个 **skill**（系统指令 + 领域知识） | 护城河；由 Orchestrator 注入模型 |
| 推理模型 | **DeepSeek-V4**（OpenAI 兼容） | 分级/拆解/差异化改写/跨语域还原 |
| 语音 STT | **MERaLiON**（api.meralion.ai） | 女佣/雇主语音输入转文字（English/Singlish 等） |
| 数据 | **Railway Postgres**（JSONB） | 7 张表，见第五节 |

### 判断稳定性：temp=0 + 强上下文 + 重置按钮
demo link 是公网给评委戳的，LLM 判断在边界会抖，绝不能当场打脸。三层兜底：
1. **判断调用 `temperature=0`**（不是 0.2），最小化抖动。
2. **靠强上下文锁定答案**：seed 家庭已预置"食欲下降 2 次 + 3 天前调降压药"，Day5 头晕在此上下文下是**强烈无歧义的 escalate**。提交/录制前，**评测（女佣 4/4）必须在 temp=0 下反复稳过**，把黄金路径验死。
3. **重置按钮（P0）**：评委可能自己乱加观察改了上下文，一键重置回 seed 状态，保证黄金路径永远可从干净起点复现。
4. **不做输出固化/假数据**：一旦被发现是放录像，比偶尔抖动更伤诚实性。

### 部署与安全（Vercel + Railway，尽量简单）
1. **key 只在服务端（Railway 环境变量）**，永不进前端打包产物。DeepSeek/MERaLiON 的 key 都在后端。
2. **模型账户设硬预算上限/低额度**：最坏情况是"跑不动"，不是收到大账单。
3. **链接私有**：用猜不到的随机 URL 发评委，不做登录；不放心可加一个共享口令（一行判断）。
4. **评审窗口期保活**：keep-alive 定时 ping 或 Railway 最低档常驻，避免冷启动卡顿。
- 明确不做：完整限流、验证码、用户系统——对私有评审链接是过度工程。

### CI/CD（push 到 main 直接上线）
- GitHub 仓库（`juliawangjiayu/agewell`，私有）直连 **Vercel（前端）+ Railway（后端）**，原生"push→自动构建部署"，不写复杂脚本。
- **不搞分支**：push 到 `main` 直接上线（团队不做大改，接受此简单法）。
- CI：加一个极小 `.github/workflows/ci.yml`，push 时跑后端 pytest，拦下坏提交再上线。

> **WorkBuddy 不进 demo 运行时**，只作 PPT 里"判断层就是一个 Skill、任何人装上即用"的可分发性叙事。
